# Datasets

All data in this folder is open or synthetic. Nothing real or personal is used. Large downloads and
intermediate files are generated by scripts into `raw/`, which is not committed. The generated
fixtures are small enough to commit.

Two sample legacy systems are built, each with controlled defects and a ground truth file:

| Scenario | Legacy system | Source data | Target schema |
|---|---|---|---|
| Commerce | SQLite database with cryptic names, text dates and text money | Chinook | `targets/commerce_target.json` |
| Clinic | .NET assembly `ClinicDesk.dll` and its proprietary binary file `clinic.cdb` | Synthea | `targets/clinic_target.json` |

The migration platform never reads `ground_truth.json` or `expected/` during a run. Only the evaluation
harness does.

## Layout

```
datasets/
  scripts/
    fetch_chinook.sh             download and verify the Chinook SQLite file
    generate_synthea.sh          generate synthetic patients as CSV
    build_legacy_commerce.py     make the legacy SQLite fixture from Chinook
    inject_defects.py            controlled data quality problems (used by both builders)
    prepare_clinic_inputs.py     select Synthea rows, inject defects, write ground truth and expected output
    build_legacy_clinic/         ClinicDesk .NET app (C#) and build.sh
    clinic_mapping.py            true mapping of the clinic fields to the target schema (ground truth only)
    cdb_codec.py                 independent Python reader and encoder for the .cdb format (tests and expected output)
    make_targets.py              writes the target schema files
    build_all.py                 rebuilds everything, writes checksums.json
    verify_fixtures.py           compares the files on disk with checksums.json
  raw/                           git ignored downloads and intermediate files
  fixtures/
    commerce/commerce_legacy.sqlite     legacy style SQLite file
    commerce/ground_truth.json          true column rename map, true field mapping, defect list
    clinic/ClinicDesk.dll               compiled legacy .NET assembly
    clinic/clinic.cdb                   proprietary binary data file
    clinic/layout.json                  true record layout, written by ClinicDesk itself
    clinic/ground_truth.json            layout plus true field mapping (merged from clinic_mapping.py) and defect list
  targets/                       canonical target schemas with field descriptions
  expected/                      clean reference output in the target schema, per scenario
  checksums.json                 SHA-256 of every generated file
```

## Rebuild

Requirements: Python 3.12, Bash, `curl`, and either Docker or a local Java runtime and .NET SDK. The
scripts use a local `java` and `dotnet` when present and otherwise the pinned images
`eclipse-temurin:21-jre` and `mcr.microsoft.com/dotnet/sdk:8.0`.

```
make datasets          # delete every generated file and rebuild from scratch (a few minutes)
make datasets-quick    # rebuild but reuse the generated Synthea output
make datasets-verify   # check the files on disk against checksums.json
```

Without `make`: `python datasets/scripts/build_all.py --clean`.

A rebuild from scratch (including a fresh Synthea run and a fresh compile of `ClinicDesk.dll`) produces
byte identical files. The tests in `backend/tests/test_datasets.py` check the checksums, rebuild the commerce
fixture twice, and re-derive the clinic inputs and defects from the Synthea output. Set
`RUN_DOTNET_REBUILD=1` to also rebuild the binary fixtures.

How `build_legacy_commerce.py` turns Chinook into a legacy system:

| Legacy table | From | Notes |
|---|---|---|
| `CUST_MST` | `Customer` | columns such as `cust_no`, `f_nm`, `l_nm`, `email_adr`, `addr1`, `zip_cd`; `fax_no` has no target |
| `PROD_MST` | `Track` joined to `Genre` | `prod_nm`, `cat_nm` (genre name), `unit_prc` as text; `comp_nm`, `len_ms`, `sz_bytes` have no target |
| `INV_HDR` | `Invoice` | `inv_dt` as text in three formats, `inv_tot` as text, `stat_cd` integer, `bill_addr1` has no target |
| `INV_DTL` | `InvoiceLine` | `qty`, `unit_prc` as text |

- Dates (`inv_dt`) are stored as text in `MM/DD/YYYY`, `YYYYMMDD` or `DD-Mon-YY`, chosen per row.
- Money is stored as text, and about a quarter of the values carry a `$` prefix.
- Status codes `1`, `2`, `3` (completed, pending, cancelled) have no lookup table. The mapping is in the ground truth.
- Tables have no primary keys, foreign keys or constraints. The database also holds three indexes, one view
  (`V_CUST_LIST`), one trigger and an empty log table `SYS_LOG`, so discovery covers every object kind.
- Not used: Employee, Artist, Album, Genre (other than the join), MediaType, Playlist, PlaylistTrack.

## Source 2: Synthea (clinic)

- What: open source synthetic patient generator. The output is not real patient data.
- Where: https://github.com/synthetichealth/synthea, release `v4.0.0`, `synthea-with-dependencies.jar`
  (SHA-256 in the table below, verified by `generate_synthea.sh`).
- License: Apache License 2.0, copyright The MITRE Corporation. See https://github.com/synthetichealth/synthea/blob/master/LICENSE.
- Generation command (run by `generate_synthea.sh`):
  `run_synthea -p 500 -s 42 -cs 42 -r 20260101 Massachusetts --exporter.csv.export=true --exporter.years_of_history=3 --generate.thread_pool_size=1`.
  CSV export is off by default so the flag is required. The seeds, the fixed reference date and a single worker
  thread make the output repeatable. One value is not: Synthea stamps an ongoing encounter with the wall clock
  time of the run, so `prepare_clinic_inputs.py` clears any `STOP` after the reference date (meaning still open).
- Subset used: the first 300 patients (306 records with deceased replacement patients are present in the
  output, the count is in the ground truth), every encounter, condition and medication of those patients,
  and at most 20 observations per patient. The full output is about 280 MB, the subset keeps the committed
  fixture near 3 MB. Five Synthea files are used: `patients`, `encounters`, `conditions`, `medications`, `observations`.

`ClinicDesk` (`scripts/build_legacy_clinic/`, C#, .NET 8) imports the five CSV files and writes `clinic.cdb`.
It is compiled with deterministic settings to `ClinicDesk.dll`. The platform analyses the assembly and the data
file without running them.

### The `.cdb` file format

| Part | Layout |
|---|---|
| Header (96 bytes) | magic `CDB1`, version `1`, code page `1252`, table count `5`, header size `96`, then a directory of five 16 byte entries (table id, record size, record count, data offset) |
| Records | five tables written one after another: patients, encounters, conditions, medications, observations |
| Size rule | `96 + sum(record count * record size)` equals the file size |

Storage conventions: fixed width text padded with spaces in Windows-1252 (longer text is truncated, characters
the code page lacks become `?`), dates as whole days since 1900-01-01 (`0` means no date, `-1` an unreadable
date), timestamps as whole minutes since 1900-01-01 (seconds are dropped), money as integer cents, packed bit
flags for patients (bit 0 male, bit 1 deceased, bit 2 hispanic, bit 3 married, bits 4 and 5 race), a one byte
code for the encounter class, and one big endian field (`ENCNTR.CostCents`) among little endian fields.
References hold the record number of the target, `0` for none and `9999999` for a reference to a record that
does not exist. Field names, offsets and meanings are in `fixtures/clinic/layout.json`.

Because `ClinicDesk` writes timestamps as minutes and Synthea times have seconds, expected timestamps end in
`:00`. The Phase 8 transform rules need an `epoch_minutes_to_timestamp` step next to `epoch_days_to_date`.

## Defect injection

`inject_defects.py` uses a fixed seed (42, derived per table) and records every change in `ground_truth.json`.

| Defect | Share of rows | Applies to |
|---|---|---|
| duplicate | 2% | every table: an exact copy is appended |
| null required field | 3% | a required field is emptied |
| invalid date | 3% | order date, birth date, encounter, condition, medication and observation dates |
| trailing spaces or mixed casing | 3% | text fields (clinic: casing only, because fixed width storage pads text anyway) |
| out of range number | 2% | prices, totals and quantities (commerce), costs and expenses (clinic) |
| orphan foreign key | 1% | references that point at no existing row |

Each affected row has at most one defect. Each entry names the table, the row (`rowid` for commerce, record
index for clinic), the column, the original and injected values, and the expected outcome: `quarantine`
(with a reason code), `deduplicate` or `normalize`. Plausible ranges used for out of range checks: unit price
0 to 1,000, order total 0 to 100,000, quantity 1 to 1,000, costs 0 to 1,000,000 dollars.

`expected/` holds the clean rows in the target schema before defects were injected. Foreign key columns hold the
`source_key` of the referenced row. The expected loaded set for a run is the clean rows minus the rows whose
defect has the outcome `quarantine` or `deduplicate`.

## Target schemas

`targets/*_target.json` list every target field with: `table`, `name`, `type`, `required`, `description` (one
plain sentence), `synonyms`, `examples` (three values) and `pii`. The field names equal the columns of the
`warehouse` tables created in Phase 1, and a test keeps them in step. Every table also has a `source_key` field
that receives the identifier from the legacy system.

## Demo experience

The seed script (added with the API phase) registers both scenarios as selectable sample legacy systems, using
the fixture files in this folder. Each scenario must complete end to end in under three minutes on a laptop.
